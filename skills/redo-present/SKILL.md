# Redo Present

Use the bundled viewer and assembler; do not recreate them. Resolve all paths relative to this SKILL.md, never to a developer's machine. Python 3.9+ and a browser are required. Write working files in the user's project, outside this installed skill.

## Brand and source material

Identify the requested client, business task, audience, source content and output format. Read the client's supplied brand rules, template catalog, fonts and assets. If a `clients/<client>/` library exists in the user's project, use it. A neutral 53-layout library is bundled at `assets/templates/neutral/`; read its [adaptation instructions](assets/templates/neutral/instructions.md) when using it. When creating a client template, follow the separate [client styling guide](assets/templates/neutral/client-styling.md): replace the demonstration pattern with the brandbook pattern, or omit patterns entirely if none exists. It includes Helvetica/system fallbacks, replaceable black/white/blue tokens, a wave mask and anonymous placeholders. Use it when a neutral template is requested or as a starting point to apply the supplied brand. No real client assets are bundled. If essential branding or source content is missing, ask for it rather than silently substituting another client's style.

Before creating slides, inspect what the user has already provided and ask for missing inputs together:

- If no presentation content was supplied, ask: «Пришлите содержание: текст, тезисы, документ или исходную презентацию. Если контент нужно разработать с нуля, укажите тему, цель и аудиторию». Do not substitute demonstration content or invent the client's business facts. Proceed with drafting from scratch only when requested, using the agreed content-expansion scope.
- If no style source is supplied or available in the selected client library, ask: «Пришлите файл стиля или брендбук, либо ссылку на Figma/папку с шаблоном». A supplied style file or explicit choice of the neutral template satisfies this requirement; do not ask again.
- If multiple styles are available and none has been selected, list their actual names and ask «В каком стиле работаем?» Wait for that choice before styling; do not mix styles or silently choose the first. Save the selected style and its source in the brief.

Keep brand rules in that client library, not in this generic skill. Preserve source wording, repetitions, facts and caveats. The mandatory content review below precedes design generation. Do not treat an agent-authored outline as user approval. Preserve the original deck unless replacement was requested.

## Content scope and photographs

Use only the supplied text by default, verbatim. Do not delete repeated introductions, condense, paraphrase, add conclusions or change wording unless the user explicitly requests that editorial work. Structural splitting and grouping do not authorize rewriting. If the user asks to develop content from scratch or expand it, follow that scope, then submit the resulting content through the same review step. Do not ask whether additions are allowed when a source-only workflow already satisfies the request.

Request photographs early, unless suitable files have already been supplied or the user has explicitly chosen a presentation without photos or another image source. Explain the naming workflow in the user's language, for example:

> Пришлите фотографии для презентации или укажите папку с ними. Понятные названия — например, «команда», «фасад», «номер люкс» — помогут определить, что изображено и на какой слайд поставить фото. Если названия технические, например IMG_001, я посмотрю сами изображения и подберу размещение по их содержанию. Переименовывать файлы необязательно.

Use descriptive filenames and folder names as placement hints, then visually inspect the photos to verify subject, orientation, quality and cropping. For generic or absent descriptive names, inspect each image and infer a suitable slide from visible content and the slide's message. Do not infer a person's identity, an exact location or product model from appearance alone; clarify only if that distinction matters. If a filename conflicts with the image or its intended use is ambiguous, flag the mismatch instead of assigning confidently. If image inspection is unavailable, explain that and request short descriptions rather than pretending to have seen the photos.

Record the selected image-to-slide mapping in the project so the five design alternatives use appropriate assets consistently. If photos are unavailable, ask whether to proceed without photos, with clearly identified placeholders, or with generated/sourced images. Do not silently present template imagery as the client's real photographs. Reuse any already-stated preference rather than repeating this question.

## Mandatory content review — before any design variants

For a new presentation, read [the content-review workflow](references/content-review.md). Prepare small semantic blocks around 250 characters, retaining exact source wording. Preserve semantic formatting: H1/H2/H3 headings, paragraphs, ordered/unordered lists and tables with header and body cells. Store these as structured content nodes, not flattened plain text. Keep lists and tables whole even when they exceed the approximate 250-character target. One block becomes one initial content slide. Copy the bundled content planner into the working project, preload your plan, and open it for the user. The user groups adjacent slides by drag-and-drop and inserts section dividers.

**STOP after opening the content planner. Wait for the user to return its `presentation-structure-v1` markup to this chat. Do not create design variants, run design prepare, or open the design selector before that return.** Merely producing an outline, deciding that text is crowded, or independently splitting eight source pages into thirteen slides does not satisfy this gate. Do not claim that showing the structure is optional.

If the user already supplied a reviewed structure, resume from it without repeating review. Only a direct, explicit user instruction to skip structure review overrides this default; a generic “make a presentation” does not. Record the returned structure as `approved-structure.json` in the project. Preserve its slide order, block grouping and divider titles throughout design generation. If fitting requires regrouping, return to content review rather than silently changing it.

## Create alternatives

Enter this stage only after the content-review gate above is satisfied. Read [the bundle format and commands](references/format.md). Store canonical text in content.json and retain each approved block’s content tree/semantic HTML separately in approved-structure.json. Render heading levels, lists and table rows/cells in all five designs; do not flatten them into paragraphs. Text equality alone does not prove structural fidelity. Create exactly five appropriate compositions per slide with the same content: variants 1–3 adapt three distinct layouts from the selected style library; variants 4–5 are newly designed by this skill in that same style. Record `origin: "library"` and an actual `templateRef` for variants 1–3, and `origin: "generated"` for 4–5 in variants.json. Do not label an invented layout as library-derived. If fewer than three suitable source layouts exist, ask the user whether to supplement the library or allow more newly generated layouts. The two new layouts must also differ from the library choices; five recolorings are not five designs. Layout choices must differ in spatial arrangement, hierarchy, image placement or content grouping; a different color or pattern alone is never another layout. Compare all five with the same plain background before delivery and replace duplicates with distinct compositions. Follow client-specific rules on typography, imagery, backgrounds and narrative rhythm. Keep content and designs separate. Provide a per-slide background picker using accessible circular color swatches, including patterned swatches and an original/reset swatch: define client-approved `backgroundOptions` in content.json and mark background surfaces and their foreground text as described in the bundle format. For each allowed color, offer plain and patterned options using the same layout, only when the brandbook provides a pattern. Keep patterns disabled on layouts whose styling rules forbid them. If the brand has no pattern, offer plain colors only. Check contrast for every offered color; preserve photos. Verify the chosen background is visibly painted, not merely set in computed CSS: gradients, opaque full-slide wrappers and negative stacking layers can hide it. Mark the actual opaque surfaces, keep decorative patterns behind content but above the canvas, and never remove intentional photos to reveal a background. For full-photo compositions, explain that only exposed canvas areas change. Background choices must survive preview, export and final assembly.

Generate static HTML variants and variants.json. All dependencies must live inside the working bundle. Run the bundled `scripts/studio.py validate` and `prepare` commands with absolute paths. Prepare copies the existing `assets/viewer/` into the bundle and records its identity; do not generate a new selector. Visually inspect every variant for loading, clipping, collisions and readability. Text validation is not a substitute for visual inspection.

Open the bundle's selector.html, preferably through a loopback-only local HTTP server rooted at the working project. Reuse an existing suitable server when available. The selector is a vertically scrolling deck with slide navigation on the left and five variants on the right of each slide. Variant 1 is selected by default; clicking a variant immediately saves that choice, with no confirmation button. Give the selector link and wait for the user to return their list or selection file before assembly; default values alone do not mean the user has finished reviewing. If the user explicitly bypasses this stage or requests a different scope, honor the request.

## Assemble the chosen presentation

Accept the downloaded selection.json or a number list. Identify the reviewed project and version. For a plain list, use the fingerprint from that reviewed manifest, not a regenerated set. Ask only if the intended set is ambiguous or the list invalid. If backgrounds were changed, use the full selection JSON/file containing `backgrounds`; a bare layout-number list cannot preserve those colors.

Run `scripts/studio.py assemble` to a new output directory. It copies the chosen designs without regenerating them. Preserve selections even if their combination could improve in rhythm; report suggestions separately. Verify the assembled presentation loads with its dependencies.

Deliver HTML by default. If the requested output is Figma, PowerPoint or another format, continue using available format-specific tools and skills, transfer only selected designs, and visually verify the result. This package does not provide those exporters or account access. Do not call HTML delivery complete when another format was requested. Preserve editable text when supported and disclose any font/vector limitation.
